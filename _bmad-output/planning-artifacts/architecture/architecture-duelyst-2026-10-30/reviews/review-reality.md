# Reality check: Duelyst rules architecture spine

Verdict: **revise before finalizing**. The match-scoped profile and shared SDK boundary fit the code, but several existing seams need explicit rules to avoid an implementation that satisfies the prose while breaking a mode or replay.

## Findings

### High — axial positions require an SDK-wide data boundary, not view-only conversion

AD-2 and the Coordinates convention say new-match positions serialize as `{q,r}` and convert at the view boundary. Today the SDK stores and reads `{x,y}` throughout `Board`, `GameSetup`, actions, entities, and card effects; a search for `position.x`, `position.y`, or `getPosition().x/.y` in `app/sdk` finds 178 matches. `GameSetup.addCardsToBoard` passes `position.x, position.y` (`app/sdk/gameSetup.coffee`), while `GameSession.deserializeSessionFromFirebase` reconstructs a `Board` before cards (`app/sdk/gameSession.coffee:3418+`). State explicitly serialized as `{q,r}` would break these paths unless the contract says all SDK position producers/consumers become profile-aware, with a single adapter for old `{x,y}` data. Change the convention from “view boundary” to “all SDK and serialization boundaries,” and specify which shape a new-mode SDK action receives.

### High — global hand size and draw paths must dispatch through the ruleset

`Deck` sizes `@hand` and loops over `CONFIG.MAX_HAND_SIZE` in multiple methods (`app/sdk/cards/deck.coffee:27,170,180,199,216,262,353`); the game player view also reads it (`app/ui/views/layouts/game_player.js:418`). The turn queue calls `actionsDrawNewCards()` on the ending player's deck (`app/sdk/gameSession.coffee:1832+`). AD-4 specifies eight slots and no draws but should bind **every hand-capacity and hand-mutation entry point** to the match profile, including `Deck` construction/deserialization, `applyCardToHand`, and the game view. A global change from 6 to 8 would alter legacy modes.

### High — existing API validation bypasses rules on common environments

`UsersModule.isAllowedToUseDeck` returns success before checking the general, count, or card IDs whenever `allCardsAvailable` is set and `forceValidation` is false (`server/lib/data_access/users.coffee:739-749`); `/single_player` calls it without force (`server/routes/api/me/games.coffee:363`). The new nine-card/allowlist gate must execute ahead of that bypass, or be separately invoked at the Practice entry. The local Sandbox path (`app/sdk/challenges/sandbox.coffee`) has no server entry, so its SDK setup validation must be authoritative locally; AD-4's blanket “server entry validation is authoritative” does not describe that path.

### Medium — profile restore order must be specified for replay setup

`GameSetup.setupNewSessionFromExistingSessionData` reconstructs players, draw piles, hands, and board from `gameSetupData` (`app/sdk/gameSetup.coffee:215-250`), and `GameSession.deserializeSessionFromFirebase` creates `Board` before restoring cards (`app/sdk/gameSession.coffee:3418+`). If a saved new-mode session restores `legacy` by default until after setup, new axial positions and eight slots are interpreted incorrectly. Require resolving the stored ruleset ID before board/deck construction and before replay actions, with legacy fallback only when the ID is absent.

### Medium — Practice bot and starting hand are currently generated by legacy paths

`createSinglePlayerGame` calls `UsableDecks.getAutomaticUsableDeck` when no AI deck ID is provided (`server/lib/create_single_player_game.coffee:90+`); the route passes an AI starting hand size based on difficulty and `CONFIG.STARTING_HAND_SIZE` (`server/routes/api/me/games.coffee:400+`). The new-rules profile must replace both for Practice: select the specified fixed bot deck and create all eight opening cards regardless of difficulty. The spine's generic allowlist statement does not currently bind these two launch decisions.

### Medium — the Spec still names legacy start coordinates

`SPEC.md` and `rules-detail.md` say `(0,2)` and `(8,2)` while AD-2 chooses axial `(-2,4)` and `(2,4)`. The user explicitly chose axial addresses for corresponding left/right center cells. Update the source package or state both coordinate systems there so the implementation cannot follow mutually inconsistent documents.

## Confirmed fit

- `SandboxDeveloper` inherits Sandbox mode setup and then enables developer mode (`app/sdk/challenges/sandboxDeveloper.coffee`), so AD-1 correctly rejects `GameType.Sandbox` as the sole selector.
- `GameSession` serializes public `gameType` and `gameSetupData` via `JSON.stringify` (`app/sdk/gameSession.coffee:3400+`), supporting a persisted profile ID and version.
- `server/lib/create_single_player_game.coffee` sets `gameType` before `GameSetup.setupNewSession`, and `Challenge.setupSessionModes` runs before local setup, so entry-time profile selection can precede game initialization.
- The repo already shares `app/sdk` between browser and server; no added framework or service is necessary for the proposed profile.
