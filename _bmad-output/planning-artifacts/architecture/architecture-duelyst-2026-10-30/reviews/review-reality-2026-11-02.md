# Reality check: ARCHITECTURE-SPINE.md (AD-1, AD-2, AD-3, AD-5, AD-6, AD-7, AD-8)

Date: 2026-11-02. Reviewer: independent. Code: submodule `duelyst/app/sdk` (CoffeeScript). No edits made.

## Verdict
The spine is largely accurate and feasible; named helpers and files exist. Two spine statements are wrong or self-contradictory (AD-6 wording, AD-2 start cells), and several target decisions (AD-7 General state, AD-8 single resolver, Phase keyword, AD-3 ordering) are not yet implemented.

## Confirmed (spine matches code)
- `Rulesets.isPracticeSandboxV2(id, version)` in `rulesets/rulesetsLookup.coffee:16`; `GameSession.getIsPracticeSandboxV2` at `gameSession.coffee:892`. No inline ID+version comparisons exist; only the helper compares version. Ruleset lookup rejects unknown ID/version (`setRuleset` throws); missing ID defaults to legacy.
- `p_endTurn` (`gameSession.coffee:1339`) is invoked only from `EndTurnAction`; it decrements counters for entities owned by the ending player (incl. untargetable), then transfers `min(3, reserve)`. Both are deterministic and run in the action execution loop, so replay-safe. Decrement is guarded by `!currentTurn.getEnded()`.
- Entity accessors exist: `getUsesActionPoints`, `getActionPoints`, `spendActionPoint`, `getCanMove`, `getCanAttack`, `getIsExhausted`; `initializeActiveAbility` (explicit, not in a getter), `decrementActiveAbilityCounters`, `startActiveAbilityCooldown`, `clearActiveAbility` (called from `Unit.onRemoveFromBoard`).
- The General is a `Unit` (extends `Entity`), so it can hold `activeAbilityState`. Serialization carries it: it is in `createCloneCardData` and `getCardDataKeysForCopy` (entity.coffee:96, 104), and Card serializes own properties that differ from the prototype.
- `UseActiveAbilityAction` and `PlaySignatureCardAction` are registered in `actionFactory.coffee`; use checks both counters zero, active, not silenced, and spends one AP; resolves via `PlayCardAction` with `effectCardId`.
- Opening reserves 17/16 set in `gameSetup.coffee:145-148`. Bot roster in `cardEligibility.coffee` (10979, 19052, 19038, 10205, 10001, 19051, 10954, 10206) matches `practice-bot-deck.md` exactly; Planar Scout (10019) is deck-only; `CONFIG.MAX_NEW_RULES_DECK_SIZE = 9` (general + 8).
- Defaults: `Unit` speed `CONFIG.SPEED_BASE` (2), reach `REACH_MELEE` (1), movementType walk, level 1; `getAttackType` falls back to "melee". Stat fields are in copy keys.
- `ModifierPhasing` differs from `ModifierFlying` in movementRange: both cross terrain; only Phasing passes through enemy units (`movementRange.coffee:44-49`).

## Spine ERRORS (spine mis-describes reality or is internally inconsistent)
1. AD-6 says modifiers, actions, and validators "never branch on action points or ruleset version themselves". AD-1 mandates they call the version helper, and the code legitimately does so (ModifierPhasing, movementRange, validators). Reword AD-6 to "never branch on the ruleset version except via the AD-1 helper, and never on action points at all".
2. AD-2 says "The general start cells are (-2,4) and (2,4)" in the version 1 board paragraph. Code: v1 uses (-1,2) and (7,2) and v2 uses (-2,4) and (8,0) (`gameSetup.coffee:76-99`). Neither matches (2,4). The coordinate frame used by `addGeneral` for these values was not confirmed (x/y vs q/r parameter names). Reconcile the spine with `map-layout.md` and the code, or state the frame explicitly.
3. AD-6 "Phase is a keyworded modifier in the style of Flying": `ModifierPhasing` has no `@isKeyworded`, name, or definition (unlike `ModifierFlying`). Either the claim is a target (move to follow-up) or the spine should say "non-keyworded modifier". Note also `getMovementType` returns "phase" if `movementType` is set, not only via modifier, so Phase has two sources.

## Code diverges, needs follow-up
1. AD-7: `Player.signatureAbilityState` (player.coffee:45, 368-382), `initializeSignatureAbilityState` called from `setRuleset`/`gameSession:3586`, `p_endTurn` calls `currentPlayer.decrementSignatureAbilityCounters()`, and `PlaySignatureCardAction` reads player state. The spine says no player-level ability state exists. The General has no `activeAbility` definition (only signature card data carries one), so `initializeActiveAbility` is a no-op for Generals. Migrating is feasible (General is a Unit) but touches `getIsSignatureCardActive`, the UI hand-slot lookup, and replay of existing v2 saves (serialized `signatureAbilityState` would need a migration or the spine needs an explicit compat note).
2. AD-8: no single shared resolver. Wall blocking via `segmentEntersHexInterior` is duplicated in `attackRange.coffee:154`, `spell.coffee:164`, and `attackAction.coffee:84-93` (`_hasAreaDelivery`). `AttackAction` computes area geometry itself (violates "does not compute geometry itself"). The target-supporting-Wall exception exists in each copy (distance 0 skip) but is copied, not shared. Lobbed-ignores-obstruction not verified.
3. AD-6 "area reuses existing mechanics": two area mechanisms coexist in v2. `AttackAction` stat-driven area (own `attackType == 'area'`, hex distance) vs `ModifierBlastAttack` (cardinal-axis, `getEnemyEntitiesOnCardinalAxisFromEntityToPosition`, `PATTERN_BLAST`). `getAttackType` returns "area" for Blast but `_isVersion2StatDrivenAreaAttack` requires an own `attackType`, so Blast units take the legacy path in v2. Decide whether Blast is retired, remapped, or excluded by eligibility.
4. AD-6 action-point authority: `AttackAction` (line 65-66) and `PlaySignatureCardAction` (line 25-26) and `UseActiveAbilityAction` query/spend AP directly instead of through a single Entity accessor path (spend is on Entity, but check `getActionPoints() > 0` is inline in PlaySignature). Acceptable for spend, but not "accessors only decide".
5. AD-3: `p_endTurn` performs the mana transfer and decrements before `currentTurn.setEnded(true)`; spine says "after ending the turn". Also the mana transfer is gated by `getRulesetId() is "practice-sandbox-hex"`, so it runs for v1 and v2; spine says opening/turn-end behavior for the new ruleset generally, which is consistent, but the v2-only decrement and the all-versions transfer should be stated.
6. AD-1: server derivation is `getServerRulesetForGameType`: every `GameType.SinglePlayer` gets v2, not "the validated Practice route" (`create_single_player_game.coffee:179`). Confirm no other flows (challenges, tutorials, boss battle) share SinglePlayer. BossBattle maps to legacy (tested). Local Sandbox derivation from the concrete class was not located in this review.
7. AD-1 note: many checks still compare `getRulesetId() is 'practice-sandbox-hex'` (ID only, version-agnostic: spell.coffee, gameSetup, validators, many actions). The helper rule is satisfied literally, but the spine should explicitly allow an ID-only "hex family" check, otherwise it reads as violated.
8. AD-4/5 related: the eligibility check `isNewRules` uses ID only (any version), so v1 and v2 share the allowlist; consistent with spine, noted for clarity.
