## Intent

**Problem:** `ModifierPhasing` is a bare copy of `ModifierFlying` without the keyword fields (`isKeyworded`, modifier name, keyword definition, FX resource, localized strings), so Phase does not read as a keyword and the two can drift (CAP-1, spine AD-6).

**Approach:** Rebuild `ModifierPhasing` as a Flying-style keyworded modifier that differs from Flying only by passing through enemy units and being active only in version 2, with its English strings added next to Flying's.

## Boundaries & Constraints

**Always:** Phase stays version 2 only (inactive elsewhere) and keeps `type`/`@type` `"ModifierPhasing"`, `maxStacks: 1`, and the infinite speed buff. Fly and phase keep identical hole and Wall permissions; only passing through enemy units differs, still decided in movement range. Movement type derivation keeps returning `phase` for a Phase unit. Keyword copy: name "Phasing", definition "Can move to any location on the battlefield, including through enemy units. Cannot stop on an occupied tile." Flying and legacy behavior are unchanged.

**Never:** Make Flying-specific checks treat a Phase unit differently from today, change movement or attack geometry, add FX assets, or edit other languages' strings beyond what the repository's locale tooling requires. Do not let Flying's keyword list or text change.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| PHASE_V2 | Version 2 unit with Phasing | Active; derives movement type `phase`; passes through enemy units, crosses holes and Walls like Flying | N/A |
| PHASE_NON_V2 | Legacy or version 1 unit with Phasing | Modifier inactive; no effect on speed or movement | N/A |
| KEYWORD | Phasing keyword lookup | Has name and definition strings, shows as a keyword like Flying | Missing string is a test failure |
| FLYING | Flying unit in any ruleset | Behavior and keyword text identical to today | N/A |
| FACTORY | Modifier factory with type `ModifierPhasing` | Returns the class; context object round trip works | N/A |

## Implementation Notes

- `ModifierPhasing` gained `@isKeyworded`, `@modifierName`, `@keywordDefinition`, `@description`, and `fxResource`, plus an empty `ModifierPhasing` FX entry in `app/data/fx.js` (no assets) and the `phasing_name` / `phasing_def` English strings in `locales/en/modifiers.json`. `locales/en/index.json` is gitignored and generated by `gulp/localization.js`, so it was not edited.
- Deliberate deviation: Phase does not subclass Flying. `hasModifierClass` and `getModifierByClass` use `instanceof`, so a subclass would make every Flying check (movement range, the Flying visual, Flying-based cards) match Phase units. "Flying style" is met through the shared keyword fields and speed buff; a test asserts Phasing is not an instance of Flying.
- `Entity.getMovementType` uses `hasModifierClass`, so an inactive Phasing modifier outside version 2 still reports `phase`; that predates this story and was left unchanged.
- Review: subagent layers were skipped for this mechanical change; behavior is pinned by `phase_keyword.js` (only KEYWORD fails on the old code) and the full unit sweep. `test/unit/misc/hex_view.js` has one slow-test timeout that also fails on the pre-change code.
